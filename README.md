# shukatsu-tracker

[![CI](https://github.com/Natto2026/shukatsu-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/Natto2026/shukatsu-tracker/actions/workflows/ci.yml)
![Python](https://img.shields.io/badge/python-3.11%2B-blue)
![License](https://img.shields.io/badge/license-MIT-green)

選考プロセスをローカルで安全に管理するツールである。締切・選考ステップ・提出した回答を
一元管理する。認証情報を持たず、既定では外部と通信しない設計である。

![ダッシュボード](docs/screenshots/dashboard.png)

## なぜ作ったか

選考管理はスプレッドシートが定番で、作者自身もスプレッドシートで管理している。
そこで感じた次の課題を、設計と検証の題材として解いたのがこのアプリである。

- 締切の見落としが怖い。企業ごとにマイページへ情報が分散し、一覧性がない
- 一度書いた回答が探せない。設問・文字数制限・提出先が結びついていない
- 記録が増えても、どのステップで止まっているのかが見えない

一方で、就活の管理データはマイページのURLや登録メールを含む。クラウドの
サービスに預けるのも、スプレッドシートに認証情報を並べるのも避けたい。
そこで**既定ではデータが端末から出ない**作りにして、締切管理・回答管理・振り返りをまとめた。

**現在の利用状況**: このアプリはまだ作者自身の選考管理には使っていない。スプレッドシートからの
移行経路（CSV の取り込み、[#8](https://github.com/Natto2026/shukatsu-tracker/issues/8)）は入ったが、
作者自身のデータの移行はまだ行っておらず、自分の管理はスプレッドシートのままである。
動作はデモデータと自動テストで確認している。

## 機能

| ページ | 内容 |
|---|---|
| ダッシュボード | 7日以内の締切（期限超過は強調表示）、全社の選考状況一覧 |
| 企業管理 | 選考ステップ（ES〜最終面接＋自由追加）、締切・結果の記録、マイページURL管理、企業研究リンクの自動生成（公式・新卒採用・事業内容・IR・クチコミ・選考体験記・ニュース） |
| ES管理 | 設問と回答のライブラリ。カテゴリ・キーワード検索、文字数制限との照合（超過と8割未満を警告） |
| 添削 | 保存した回答を、書き方の観点から点検。応募業界に応じて観点を入れ替える。**既定では通信せず**、依頼文を組み立てて表示するだけ |
| 分析 | 応募経路別・適性検査タイプ別の通過率、選考ファネル |
| 取り込み | スプレッドシートから書き出した CSV（UTF-8 / Shift-JIS）で、企業と選考ステップをまとめて登録する。書き込む前に、追加される件数と、取り込まない行・列を理由つきで表示する。登録済みの企業は上書きしない |
| 書き出し | 選考記録と集計を依頼文つき Markdown に書き出す。**この画面は外部と通信せず**、何をどこまで渡すかは書き出し内容を確認して利用者が決める |

### 回答の点検

保存した回答に対して、書き方の観点から点検の依頼文を組み立てる。

![添削](docs/screenshots/review.png)

観点は Python のコードではなく `src/shukatsu_tracker/review/criteria/` の TOML に
書いてあり、編集すればアプリを変更せずに増やせる。共通の観点（設問への正対、
前提情報、専門外への翻訳、困難・葛藤、字数の使い切りなど）に加えて、応募業界ごとの
上乗せを重ねる仕組みである。業界ファイルは観点を追加できるほか、`emphasis` に
共通観点の id を並べると、その観点の重みが上がる。

```toml
# review/criteria/industry/finance.toml（抜粋）
[meta]
matches = "金融"
emphasis = ["process_behind_result", "interview_ready", "cause_analysis", "not_an_impression"]

[[criteria]]
id = "evidence"
title = "数字と根拠の確かさ"
```

実行先は2つあり、**既定は「書き出しのみ」で外部と通信しない**。
組み立てた依頼文を画面で確認し、そのまま好きな場所に貼って使える。
Claude API に送る実行先は、環境変数 `ANTHROPIC_API_KEY` が設定されている場合にだけ
選択肢に現れる。**API キーはアプリに保存も入力もしない**。SDK が実行環境の
環境変数から解決したものを使い、DB にもファイルにも書かない。

```bash
pip install -e ".[llm]"      # 通信する実行先を使う場合のみ
```

送信に使うモデルは `SHUKATSU_REVIEW_MODEL` で差し替えられる。未設定なら既定の
`claude-opus-5` を使うので、通常は設定不要である。新しいモデルに乗り換えるためにコードを直さなくて済むように
してある。

```bash
SHUKATSU_REVIEW_MODEL=claude-sonnet-5 streamlit run app.py   # 既定以外のモデルに替える例
```

所見は履歴として残る。評価した時点の本文を控えているため、あとから回答を
書き換えた場合は「この所見のあとに本文が変わっています」と表示される。

### CSV の取り込み

スプレッドシートで管理してきた記録を移すための入口である。1行目を見出し、2行目以降を
「1行 = 選考ステップ1件」とした CSV を読み、同じ企業名の行を1社にまとめる。
見本は [docs/sample_import.csv](docs/sample_import.csv)（架空の企業）にある。

- ファイルを選ぶと、まず要約（追加される企業とステップの数、取り込まない行と理由、取り込まない列）を
  表示する。「この内容で取り込む」を押すまで保存しない
- 書き込みは1つのトランザクションで行い、途中で失敗したら何も残らない
- 読めない締切や選択肢にない値を、空欄や既定値に置き換えて取り込むことはしない。行番号と理由を出す
- 企業のどれかの行に問題があれば、その企業は丸ごと取り込まない。登録済みの企業は上書きしないため、
  半分だけ入れると、CSV を直しても残りを入れる手段がなくなるからである
- マイページURL・ログインID・パスワードなど、認証情報に当たる列は読まない

列の一覧と失敗時の見え方は [docs/operations.md](docs/operations.md) にある。

## 保存先

既定は SQLite で、`data/shukatsu.db` の1ファイルに保存する。サーバーを立てる
必要はない。`SHUKATSU_DB` で保存先を切り替えられる。

```bash
SHUKATSU_DB=data/another.db streamlit run app.py                       # 別のファイル
SHUKATSU_DB=postgresql://user:pass@127.0.0.1:5432/shukatsu streamlit run app.py   # PostgreSQL
```

PostgreSQL を使う場合は `pip install -e ".[postgres]"` が必要である。手元で試すなら
同梱の `docker-compose.yml` で立てられる。

テーブルの読み書きの SQL は `db/repositories.py` の1ファイルに、スキーマは
`db/migrations/*.sql` に閉じてあり（例外はスキーマ管理そのものだけ。[CONTRIBUTING.md](CONTRIBUTING.md) に明記）、方言の差
（プレースホルダ・主キーの書き方・日付関数・例外の型）は `db/dialects.py` に
集めている。**同じテスト一式が、SQLite と PostgreSQL の両方に対して CI で走る。**

> データが端末から出ないのは SQLite の場合である。PostgreSQL を別のホストに向けた
> 場合、その前提は変わる。手元で立てたサーバーに向けるか、置き場所を
> 自分で把握したうえで使うこと。

## データの扱い（セキュリティ方針）

- **既定では通信しない**。データはローカルの `data/shukatsu.db`（SQLite）に保存する
- データが端末の外に出るのは、利用者が次のどちらかを選んだ場合だけである
  - 添削の実行先に Claude API を選んだ場合。画面で確認した依頼文（設問と回答の本文を含む）が送信される。
    この実行先は `ANTHROPIC_API_KEY` が設定されている場合にだけ選択肢に現れ、既定は通信しない「書き出しのみ」である
  - `SHUKATSU_DB` を別のホストの PostgreSQL に向けた場合。保存するデータ全体がそのホストに置かれる
- サーバーは `127.0.0.1` のみにバインドし、同一LAN内の他端末からもアクセスできない（`.streamlit/config.toml`）
- `data/` は `.gitignore` 済みで、個人の選考データがリポジトリに混入しない構成である
- **パスワードは保存しない設計**である。平文保存は漏洩リスクになるため、マイページURLと登録メールアドレスのみ管理する
- 書き出し機能にマイページURL・ログイン用メールを含めないことを、回帰テストで保証している
- CSV の取り込みは、認証情報に当たる列（マイページURL・ログインID・メール・パスワードなど）を読まない。取り込まなかった列は画面に表示する（これも回帰テストで保証している）
- 画面は、利用者がボタンを押したときだけ書き込む。開いただけで保存は走らない
- 削除は確認を挟み、何が失われるかを明示する

## セットアップ

```bash
git clone https://github.com/Natto2026/shukatsu-tracker.git
cd shukatsu-tracker
pip install -e ".[dev]" -c constraints.txt
streamlit run app.py
```

`constraints.txt` は検証済みの版に固定するためのもので、CI も同じ指定で入れている。

ブラウザで http://localhost:8501 が開く。

**デモデータで試す**（スクリーンショットと同じ架空データ）:

```powershell
python scripts/demo_data.py
$env:SHUKATSU_DB="data/demo.db"; streamlit run app.py
```

README のスクリーンショットは、このデモデータから自動で撮り直せる。
画面を変えたときに、説明と画像がずれたままにならないようにするためである。

```bash
pip install playwright
python scripts/capture_screenshots.py
```

## 設計

UI・ユースケース・永続化を層として分け、上の層が下の層だけを呼ぶ構成にしている。

```
app.py（画面）
   └─ services/（業務ルール・入力検証・トランザクションの単位）
        └─ db/（接続・スキーマ適用・テーブルごとの読み書き）
             └─ SQLite / PostgreSQL（方言の差は `db/dialects.py` が吸収する）
analytics.py（集計）は DB にも UI にも依存しない純粋関数
review/（観点の定義・依頼文の組み立て・実行先）は services から呼ばれる
```

この分け方にしている理由は3つある。

- **集計を DB から切り離す**ため。`analytics.py` は `StepView` の列だけを受け取るので、
  テストがデータを組み立てるだけで書け、画面を変えてもロジックのテストが壊れない
- **業務ルールの置き場所を1か所にする**ため。「企業を追加したら既定の選考ステップも
  一緒に入れる」といった規則を UI に書くと、別の入口を作るたびに書き直しになる
- **スキーマを追跡可能にする**ため。テーブル定義は `db/migrations/NNN_name.sql` に置き、
  適用済みのバージョンを DB 側に記録する。既存のデータを作り直さずに列を追加できる

点検機能の実行先は差し替え可能な形（共通のインターフェース）にしてある。
既定の実行先は通信しないため、通信する実装を入れても「アプリが外部と通信するかどうかは
利用者が選ぶ」という前提が崩れない。テストも、通信せずに送信内容を検証できる。

トランザクションは明示的に開き、境界の間は接続のロックを握る。接続の状態から
「いまトランザクション中か」を判定すると、別のセッションが開けたトランザクションを
自分のものと誤認し、相手の巻き戻しで自分の書き込みが消えるためである。接続自体も
ブラウザのセッションごとに持つ。

画面側は、書き込みを明示的な操作に限っている。入力欄のキーには保存済みの値を
含めていて、別の場所で更新があった場合は入力欄が最新の値で作り直され、古い表示のまま
上書きしない。保存時には表示した時点の値と突き合わせ、ずれていた行は入力を反映せず、
最新の値を表示していることを知らせる。

詳細は [docs/architecture.md](docs/architecture.md)（レイヤー設計・永続化の方針）、
[docs/data_flow.md](docs/data_flow.md)（データの流れ・ER 図・テーブル設計）、
[docs/screens.md](docs/screens.md)（画面一覧と呼ぶ層）、
[docs/operations.md](docs/operations.md)（起動と保守の手引き。起動・保存先・バックアップと復旧・スキーマ更新）を参照すること。
開発規約は [CONTRIBUTING.md](CONTRIBUTING.md) にまとめている。

## 見つけた不具合と直し方

動いているように見えるアプリを疑って総点検し、見つけた不具合は修正と一緒に回帰テストを足し、
わざと元に戻してテストが失敗することまで確かめている。症状・原因・対処・回帰テストの対応表は
[docs/known_issues.md](docs/known_issues.md) にまとめた（トランザクションの境界、古いタブからの
上書き、ドライバの例外、途中で切れた所見、選択肢外の値など）。どの修正がどの版かは
[CHANGELOG.md](CHANGELOG.md) の Fixed に対応している。

## 開発

```bash
ruff check .
ruff format --check .
python -m mypy
python -m pytest
python -m pytest -m "not ui"   # 画面（AppTest）を除いた単体だけ。数秒で終わる
python -m pytest --cov         # 網羅率も見る場合（CI でも出力している。しきい値は設けていない）
```

テストは層ごとの単体テスト（集計・リポジトリ・サービス・スキーマ適用・
トランザクション）と、Streamlit AppTest による画面のテストで構成している。
画面のテストは「例外が出ないこと」だけでなく「描画しただけで書き換えないこと」
「古い表示で新しい変更を潰さないこと」を確認する。
観点とテストの対応は [docs/test_plan.md](docs/test_plan.md) にまとめている。
画面のテストは1本あたり数秒かかるため `ui` マーカーを付けてあり、書きながら回すときは
`-m "not ui"` で外せる。PR の前と CI では全部を回す。

CI では Python 3.11 / 3.12 / 3.13 の SQLite に加えて、同じテスト一式を実際の
PostgreSQL に対しても走らせている。直接の依存は `constraints.txt` の版に固定しているので、
streamlit や ruff の更新で CI が勝手に赤くなることはない。上げるときは手元で全部通してから
`constraints.txt` を書き換える。間接の依存（numpy・pyarrow など）は固定していないため、
それらの更新で落ちた場合は、原因の版を `constraints.txt` に足して止める。

```bash
# 手元で PostgreSQL に対して走らせる場合
SHUKATSU_TEST_DSN=postgresql://user:pass@127.0.0.1:5432/shukatsu_test python -m pytest
```

通信を伴うテストはない。API を呼ぶ実行先は、差し込んだ偽のクライアントに対して
「何を送るか」「応答をどう解釈するか」だけを検証している。加えて、SDK が入っている環境
（CI の SQLite のジョブ）では、本物の SDK を通信だけ差し替えて通し、引数名や例外の型が
実際の SDK と食い違っていないことを確かめる。
